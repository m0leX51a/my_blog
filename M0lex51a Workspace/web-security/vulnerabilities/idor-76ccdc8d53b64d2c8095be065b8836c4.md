## Mechanisms

***

#### what is IDOR?

it is web vulnerability that let attacker show the other users data and perform actions like

(comment in social media sites) as another users without user permissions

#### when it happens?

IDORs happen when users can access resources that do not belong to them by directly referencing the object ID, object number, or filename.

#### Example 1

lets say that [example.com](http://example.com) allow to it’s users to chat to each other and we notice when user sign up take an **id** so when we click on view message button to view messages with friends the button redirect the user to [https://example.com/messages?user\_id=1234](https://example.com/messages?user_id=1234). , so at this point we could find IDOR vulnerability by changing the id to **1233** for example and if it vulnerable to IDOR it will show another user messages for the user who has the id **1233.**

```php
messages = load_messages(request.user_id)
display_messages(messages)
```

#### Example 2

let’s say that users can submit a POST request to change their password. The POST request must contain that user’s ID and new password

```php
POST /change_password
(POST request body)
user_id=1234&new_password=12345
```

so if application doesn’t validate the user input so it could lead to **ATO** by changing the id to **1233** to change the account password to user who has the id **1233.**

#### Example 3

this request allows users to access a file they’ve uploaded: https://[example.com/uploads?file=user1234-01.jpeg](http://example.com/uploads?file=user1234-01.jpeg). Since the value of the file parameter is user1234–01.jpeg, we can easily deduce that user-uploaded files follow the naming convention of USER\_ID-FILE\_NUMBER.FILE\_EXTENSION so we can access files that belongs to others by guessing files name .

## Hunting for IDORs

***

#### Step 1: Create Two Accounts

1. try to create tow accounts for each privilege (admin, user, group)
2. the first account will serve as the attacker to manipulate with id parameter for example
3. the second one will serve as the victim to observe the changes when the attacker account manipulations
4. repeat the testing procedure without signing in to See if you can use an unauthenticated session to access the information or functionalities made available to legitimate users.

#### Step 2: Discover Features

1. use the highest privileges to go through the application
2. try to discover as many application features as possible.
3. spot the functionalities that return user information or modify user data

some endpoints that could be vulnerable to IDOR

```bash
https://example.com/messages?user_id=1236   //This endpoint lets you read user messages:
_______________________________________________________________________________________

https://example.com/uploads?file=user1236-01.jpeg //This one lets you read user files
_______________________________________________________________________________________

POST /delete_message
(POST request body)    //This endpoint deletes user messages:
message_id=user1236-0111 
_______________________________________________________________________________________
	
https://example.com/group_files?group=group3 // This one is for accessing group files:
_______________________________________________________________________________________

POST /delete_group
(POST request body)   //This one deletes a group:
group=group3
```

#### Step 3: Capture Requests

1. Browse through each application feature you mapped in the preceding step
2. capture all the requests going from your web client to the server
3. Inspect each request carefully and find the parameters that contain numbers, usernames, or IDs.

NOTE: to make testing more efficient, use two browsers, browser to sign in with attacker account for example that has an **id=1234** and browser for victim account for example that has an **id=1233**

so when we manipulate the vulnerable parameter in attacker account we observe the result in victim account

#### Step 4: Change the IDs

finally at this stage we will switch the IDs in the sensitive requests and check if the information returned also changes

for example

This endpoint lets you read user messages: [https://example.com/messages?user\_id=1236](https://example.com/messages?user_id=1236)

if we could change the id to **user\_id=1235** and then we could show the messages of the user who has the id 1235 so we have found an IDOR vulnerability.

## Bypassing IDOR Protection

***

#### Encoded IDs and Hashed IDs

when we face a seemingly random string we will figure that it could be encoded so

will try to decode it by

1. try to figure out the encoding type by Smart Decode tool (Figure 10-2) in Burp’s decoder,
2. try to decode it to different encoding types till to find it
3. after decoding it try to change the id and encode it again and replace the old id with the new one in the request

If the application is using a hashed or randomized ID, in this case try creating a few accounts to analyze how these IDs are created. You might be able to find a pattern that will allow you to predict IDs belonging to other users.

#### Leaked IDs

It might also be possible that the application leaks IDs via another API endpoint or other public pages of the application

for example if there is an API End-Point retrieve detailed direct messages through a hashed conversation\_id value by the following request

```php
GET /messages?conversation_id=O1SUR7GJ43HS93VAR8xxxx
```

so there a case that the anyone could request a list of conversation\_ids for each user, just by using their public user ID by following request

```php
GET /messages?user_id=1236
```

#### Offer the Application an ID, Even If It Doesn’t Ask for One

the application uses cookies instead of IDs to identify the resources a user can access by the following request

```jsx
GET /api_v1/messages
Host: example.com
Cookies: session=YOUR_SESSION_COOKIE
```

it is a safe way but not totally safe because some time the developer make an alternatives ways to identify the resources a user can access the alternatives like using id so we could try to

Append id, user\_id, message\_id, or other object references to the URL query

for example the following end-point

```jsx
GET /api_v1/messages
```

so Then maybe this request would display another user’s messages instead

```jsx
GET /api_v1/messages?user_id=ANOTHER_USERS_ID
```

#### Keep an Eye Out for Blind IDORs

for example

that this endpoint on [example.com](http://example.com/) allows users to email themselves a copy of a receipt:

```jsx
POST /get_receipt
(POST request body)
receipt_id=3001
```

so when we could change receipt\_id to 3000 we could receive an email that have a receipt of another user

#### Change the Request Method

some time if the developer fails to implement the same access control for each method

so if the **GET** doesn’t return leaked data we could try to use the **DELETE** method to delete the resource instead

```jsx
DELETE example.com/uploads/user1236-01.jpeg
```

If **POST** requests don’t work, you can also try to update another user’s resource by using the **PUT** method.

```jsx
PUT example.com/uploads/user1236-01.jpeg
(PUT request body)
NEW_FILE
```

!! some times we can switching between the **POST** and **GET** methods to get the leaked information .

#### Change the Requested File Type

example, applications commonly store information in the JSON file type. Try adding the .json extension to the end of the request URL and see what happens. If this request is blocked by the server

```jsx
GET /get_receipt?receipt_id=2983
```

then try this one instead:

```jsx

GET /get_receipt?receipt_id=2983.json
```

## Escalating the Attack

***

so to get high impact

we should always look for IDORs in critical functionalities first

read-based IDORs or write-based IDORs

**write-based IDORs**: which can alter the database in an unauthorized way

looking in state changing functions (password rest ,password change ,account recovery feature)

**read-based IDORs**: which leak information but do not alter the database

looking in non-state changing functions(direct messages ,personal information, private content)

trying to combine IDORS with another vulnerability

1. **write-based IDOR** with **self-XSS** can lead to **stored XSS**
2. **IDOR** on a password reset endpoint with **username enumeration** can lead to **account takeover**
3. **IDOR** on an admin account can lead to **RCE**

***

## Prevention

***

Applications can prevent IDORs in two ways

**First:** the application can check the user’s identity and permissions before granting access to a resource. First, the application can check the user’s identity and permissions before granting access to a resource.

**second:** the website can use a unique, unpredictable key or a hashed identifier to reference each user’s resources
